6. FN-KEY / KEYBOARD REMAP (ported from the old Pop!_OS setup)

   - NOT delivered via /etc/modprobe.d/hid_apple.conf (tried first,

     boundary, before /etc/modprobe.d is reliably read yet. Confirmed via
     journalctl timestamps showing the keyboard's USB HID bind event
     essentially simultaneous with initrd-switch-root.service completing.

     reboot (not a soft-reboot).

10. FACETIME HD CAMERA: DKMS BUILD FIX (kernel 7.2 strncpy removal)
    The AUR facetimehd-dkms package (0.7.0.2) failed to build against the
    running 7.2.4-3-cachyos kernel with:
        fthd_v4l2.c:399: error: call to undeclared library function 'strncpy'
    Root cause (verified via web search, not guessed): Linux kernel 7.2
    completely removed strncpy() from the kernel after a six-year, 360+
    patch cleanup effort (landed June 2026); the function no longer
    exists in-kernel at all, not just missing a header include (adding
    #include <linux/string.h> alone did NOT fix it, confirming this).
    Fix applied directly to the DKMS-registered source (persists across
    rebuilds, unlike patching the /var/lib/dkms build/ scratch copy):
        /usr/src/facetimehd-0.7.0.2/fthd_v4l2.c line 400:
        strncpy(...) -> strscpy(...)   (kernel's own recommended replacement,
                                          same 3-argument signature, drop-in)
    Then: sudo dkms install facetimehd/0.7.0.2 -k 7.2.4-3-cachyos
    Verified working: /dev/video0 present, facetimehd-data calibration
    files (1771/1871/1874_01XX.dat, 9112_01XX.dat; same filenames as the
    old Pop!_OS backup) loaded correctly, clean ISP init in kernel log
    (firmware loaded 1392kb, DDR calibration completed, no errors).
    NOTE: this exact same strncpy fix will likely be needed again on any
    OTHER out-of-tree/AUR kernel module that hasn't been updated for
    kernel 7.2+ yet (broadcom-wl already built fine, so it doesn't hit
    this specific issue).

    which case the machine just keeps running instead of losing data --
    the failure mode itself is safe, just unpredictable). Do not rely
    on it for unattended/long-duration battery savings without
    confirming success after the fact (e.g. checking uptime/journal)
    until/unless the intermittent root cause gets identified.

14. SUSPEND-THEN-HIBERNATE -- TRIED, ROOT-CAUSED, REVERTED TO PLAIN SUSPEND
    Originally enabled as HandleLidSwitch=suspend-then-hibernate with
    HibernateDelaySec=1h (see old text below for what was tried). This
    was LATER FULLY DIAGNOSED (2026-09-12 session, after items 14/17)
    and found to have a real, structural design mismatch with this
    hardware -- not just "intermittent," a genuine root cause:

    suspend-then-hibernate is designed to arm an RTC wakealarm and
    silently transition from S3 suspend into a real hibernate-and-
    poweroff WHILE THE LID STAYS CLOSED, invisible to the user -- the
    disruptive part (real poweroff, later requiring a full cold boot to
    resume) is supposed to already be done and over with by the time you
    open the lid.
    ROOT CAUSE: `/proc/acpi/wakeup` on this machine has NO RTC entry at
    all (confirmed: LID0 is present and *enabled* as an S3 wake source,
    EC is present but disabled, but RTC doesn't appear in the table at
    all). The RTC hardware itself CAN be armed (tested directly: writing
    a future epoch time to /sys/class/rtc/rtc0/wakealarm succeeds and
    reads back correctly) -- but arming it is meaningless if the
    platform's ACPI tables never wired the RTC up as a valid wake-
    interrupt source. Confirmed empirically: during a real test with
    HibernateDelaySec=30s, the machine sat in plain S3 for ~4.5 minutes
    with ZERO wake-related kernel activity, only reacting the instant
    the lid was physically opened.
    CONSEQUENCE: since the RTC-triggered silent transition can never
    happen on this hardware, the ONLY thing that can ever wake the
    machine from the S3 phase is a real external wake source -- the lid
    switch. So opening the lid (intending to just resume and use the
    machine) is what ends up triggering the disruptive hibernate-and-
    poweroff instead, backwards from the intended design: a brief silent
    S3 wake-to-check-the-timer (fan spins briefly, screen stays off --
    this part is correct/by-design), immediately followed by the real
    hibernate write and a genuine, full poweroff (still silent, screen
    already off). The user then has to notice the machine is dead, press
    and hold power (a real off-state needs a deliberate press, unlike
    waking from suspend), see the Limine bootloader (proof it was a true
    cold boot, not a suspend-resume -- suspend-resume shows no bootloader
    at all since the CPU/RAM never lost power), and wait through a full
    boot during which the kernel finds the valid image mid-boot and
    resumes the old session instead of continuing fresh.
    Separately confirmed NOT the cause, ruled out with real evidence
    during the same investigation:
      - Wrong/stale resume_offset: re-checked live, matched exactly.
      - Missing NoCOW on the swapfile: confirmed set (lsattr showed +C).
      - HibernateMode=platform vs shutdown: tested both, both succeeded
        when actually invoked -- not the differentiator.
      - Disk/device not ready in time: the failed resume attempt's own
        log showed the device was already resolved and read successfully
        before failing on "Image not found" -- not a timing/readiness
        issue at the block-device level.
      - A real, separate, verified-via-actual-kernel-source finding along
        the way (kept for reference, NOT applied as a fix -- see below):
        kernel/power/swap.c writes the hibernation image with REQ_SYNC
        (an I/O scheduling hint) but never REQ_FUA and never calls
        blkdev_issue_flush() -- meaning on a drive with Volatile Write
        Cache enabled (confirmed via `nvme get-feature -f 0x06`: enabled
        on this exact drive), a write can be acknowledged before it's
        actually durable on NAND. This is a real, kernel-source-verified
        gap, but was NOT the explanation for the specific failure
        actually diagnosed (that one traced cleanly to the RTC/lid issue
        above), and fixing it would require either disabling the drive's
        write cache system-wide (real, permanent write-performance cost
        for all disk I/O, not just hibernate -- deliberately rejected)
        or patching and maintaining a custom kernel (deliberately
        rejected as disproportionate to a safe, low-frequency issue).

    FIX APPLIED: /etc/systemd/logind.conf changed back to
    HandleLidSwitch=suspend. Lid-open now always does a normal, instant
    S3 resume -- no hidden auto-hibernate, no surprise poweroff, no
    power-button-required wake for normal use. HibernateDelaySec left at
    1h in sleep.conf (harmless leftover, has no effect without
    suspend-then-hibernate active). Manual hibernate
    (`systemctl hibernate`) still works and was proven reliable (3/3
    real attempts succeeded when actually traced with full PM debug
    logging) -- use it directly when you specifically want the battery
    savings, rather than relying on the automatic lid-triggered version.

    GOTCHA HIT DURING THIS DIAGNOSIS: restarting systemd-logind
    (`systemctl restart systemd-logind`) while a graphical session is
    active is NOT safe -- it broke GNOME's session tracking ("Leader of
    session 'N' is gone while deserializing" in the logind log) and left
    a frozen/unresponsive GDM login prompt (spinner stopped, no cursor)
    behind a still-alive-but-orphaned gnome-shell process. Fixed with
    `systemctl restart gdm.service` (forces a completely fresh greeter +
    session from scratch). Avoid restarting logind live in the future;
    if a logind.conf change needs picking up, prefer `systemctl reload`
    if supported, or accept it'll apply next login/boot.

    ORIGINAL TEXT (context for what was tried before the above):
    Originally enabled as HandleLidSwitch=suspend-then-hibernate with
    HibernateDelaySec=1h (systemd-logind restarted to apply). Closing the
    lid suspended immediately; if it stayed suspended for over an hour,

16. SWAP MOVED TO ITS OWN @swap SUBVOLUME (fixes silent snapshot failures)
    SYMPTOM: every pacman transaction printed a confusing error on the
    NEXT transaction after this one; "Invalid snapshot '--type'."; from the snap-pac post-transaction hook.
    ROOT CAUSE (traced via dmesg + reading the actual snap-pac source,
    not guessed): the hibernate swapfile (item 13) lived inside the `@`
    root subvolume, and BTRFS unconditionally refuses to snapshot any
    subvolume containing an active swapfile; confirmed via:
        dmesg: "BTRFS warning (device nvme0n1p4): cannot snapshot
                subvolume with active swapfile"
    This made every `snapper create` call from snap-pac's pacman hooks
    fail silently (its error went to stderr, which snap-pac's
    `os.popen()` call never captures; only stdout). snap-pac then
    cached that failure's empty stdout as the "pre-snapshot number" in
    /tmp/snap-pac-pre_root, and spliced it into the *next* transaction's
    snapper command line, which shifted the `--type` flag into the wrong
    argument position; producing the "Invalid snapshot '--type'." error
    one transaction removed from the actual cause. This is why it looked
    unrelated to swap at first.
    FIX: moved the swapfile out of `@` into its own top-level `@swap`
    subvolume, matching this system's existing @home/@cache/@log/@tmp
    convention, so it's structurally outside anything snapper snapshots:
        sudo swapoff /swap/swapfile
        sudo mount -o subvolid=5 UUID=0109f7a0-... /mnt/btrfs-top
        sudo btrfs subvolume create /mnt/btrfs-top/@swap
        sudo umount /mnt/btrfs-top
        # added to /etc/fstab:
        UUID=0109f7a0-... /swap btrfs subvol=/@swap,defaults,noatime 0 0
        sudo mount /swap
        sudo btrfs filesystem mkswapfile --size 9g /swap/swapfile
        sudo btrfs inspect-internal map-swapfile -r /swap/swapfile
          -> new resume_offset: 6104320 (was 3710479; the old value in
             item 13 is now stale, physical extents moved to a new file)
        Updated resume_offset=6104320 in /etc/default/limine
        KERNEL_CMDLINE, ran `limine-update` to regenerate boot config +
        both kernels' initramfs.
    Then reclaimed the old orphaned 9GB swapfile left behind inside `@`
    (swapoff, umount /swap, rm the exposed old file, remount /swap,
    swapon again).
    VERIFIED: ran a real `pacman -S tree` transaction afterward; clean

17. NO_BATT_FIX (BD_PROCHOT disable); ported from the old Pop!_OS box
    Applied preemptively as a safety net even though this MacBook's
    battery IS currently present/detected/charging normally; the fix
    is unconditional/harmless with a working battery (just means that
    particular hardware throttle safety net never engages), and having
    it in place means if the battery ever fails/gets pulled later, the
    machine won't silently lock at ~800MHz.
    - /usr/local/bin/no_batt_fix.sh (root, no `sudo` needed; runs via
      systemd as root already, unlike the old box's user-cron version):
          r=$(rdmsr 0x1FC); f=$(( (0x$r) & 0xFFFFE )); wrmsr 0x1FC $f
      Clears bit 0 of MSR_POWER_CTL (0x1FC) = BD_PROCHOT_ENABLE.
      CORRECTED A DOCUMENTATION ERROR from the old audit while porting:
      the audit's own prose called this "bit 1 (BD_PROCHOT_ENABLE)" but
      the mask 0xFFFFE mathematically only clears bit 0; verified via
      web search against the actual documented MSR_POWER_CTL bit
      semantics (bit 0 = BD_PROCHOT enable/disable) before trusting it.
      The script's CODE was correct as inherited; only the audit's own
      English description of which bit it hit was off by one.
    - /etc/modules-load.d/msr.conf: `msr` (ensures the msr module,
      needed for rdmsr/wrmsr, is loaded at boot; msr-tools package
      was already installed this session for the C-state investigation).
    - /etc/systemd/system/no_batt_fix.service: Type=simple, oneshot-style
      (runs once and exits), After=network.target,
      WantedBy=multi-user.target, enabled.
    VERIFIED empirically, not just "should work": read MSR 0x1FC before
    (0x4005d) and after running the service (0x4005c); confirms only
    bit 0 flipped 1->0, no other bits touched. Service exited 0/SUCCESS.
    CAVEAT (not yet addressed): this only fires once at boot, same as
    the old box. The old box masked hibernate/suspend entirely (likely
    because of ITS flaky/removed battery), so a boot-only fix was
    sufficient there. THIS box actively uses suspend/hibernate (items
    14/15), and BD_PROCHOT can reassert after a resume-from-sleep, not
    just a cold boot -- a resume hook (systemd-sleep drop-in or
    WantedBy=suspend.target/sleep.target) would be needed for full
    coverage if the battery is ever actually removed on this unit.
    Flagged to the user, not yet added -- ask before adding since it
    goes beyond the literal 1:1 port from the old box.

18. SLOW/UNRELIABLE WAKE FROM SUSPEND: PARTIALLY FIXED, ROOT CAUSE OF THE
    REMAINING SYMPTOM STILL OPEN
    Symptom: user reported wake was much faster on the old Pop!_OS box.
    On this install, opening the lid sometimes shows a brief "fan bump"
    (a real, legitimate S3 wake) followed by a black screen for anywhere
    from ~4 to 40+ seconds, after which either (a) the desktop appears
    on its own, or (b) nothing happens and a power-button press is
    needed, after which the screen comes on IMMEDIATELY (not with any
    further delay) -- this specific detail (instant display-on after
    power press, regardless of how long was waited beforehand) is the
    key clue: it means the SYSTEM resumes fine and quickly, but the
    lid-open wake path specifically does not reliably result in the
    display actually being (re-)driven -- something else has to kick it.

    INVESTIGATED AND FIXED (real, kept):
    - `/proc/acpi/wakeup` showed SPIT (Apple SPI controller -- feeds the
      internal keyboard/trackpad) as S3 *disabled*. This is a real,
      concrete, verified fact: the keyboard/trackpad CANNOT generate a
      wake interrupt from real S3 suspend on this hardware -- confirmed
      when keyboard/trackpad input failed to wake a genuinely-stuck
      machine while the power button (a fixed ACPI hardware feature,
      always enabled regardless of this table) did. Enabled SPIT live
      (`echo SPIT > /proc/acpi/wakeup`) and made it persistent via a new
      oneshot unit, since ACPI wakeup states reset to firmware defaults
      every boot:
        /etc/systemd/system/enable-spit-wake.service (enabled)
        ExecStart checks if SPIT is disabled and toggles it if so.
      This gives keyboard/trackpad as an additional, gentler way to
      recover a stuck-asleep machine instead of only the power button.
      Does NOT by itself fix the root "screen doesn't turn on" issue --
      it's a recovery-path improvement, verified working.
    - `NetworkManager-wait-online.service` disabled (was taking 4.174s
      in `systemd-analyze blame`, blocking `network-online.target`).
      Legitimate minor boot-time win on its own, kept -- but DISPROVEN
      as the cause of the GDM/Plymouth delay: disabled it, rebooted,
      `plymouth-quit-wait.service` was STILL 7.223s (statistically
      identical to the 7.239s before), and the same ~4-second cluster of
      wifi-associating + Plymouth-quit-signal + gdm-greeter-session
      events still happened together at the same point in boot, just
      with the explicit wait-online dependency no longer in the chain.
      This was a real, verified-wrong hypothesis -- documented so it
      isn't re-tried.

    TESTED AND REVERTED (made things worse, do not retry):
    - Removed acpi_osi=!Darwin to test whether it was slowing resume.
      Result: resume got WORSE (9s baseline -> 17s), most likely because
      it also re-enables Thunderbolt (7 PCI bridge devices reappear in
      lspci), and while the kernel's own apple_poweroff_thunderbolt quirk
      cuts Thunderbolt's power cleanly on suspend ENTRY (confirmed via
      dmesg, took only 297ms), something about those bridges coming back
      adds real time somewhere in the resume path. Reverted immediately;
      acpi_osi=!Darwin is back (Thunderbolt disabled again, ~9s baseline
      restored). Do not remove this again for wake-speed reasons.

    STILL UNEXPLAINED / OPEN:
    - A remarkably consistent ~4-4.7 second delay shows up in EVERY
      context tested tonight -- cold boot, suspend resume with wifi on,
      suspend resume with wifi off, console-mode (no GNOME at all) --
      immune to every systemd-level change tried (disabling
      wait-online, console vs graphical). Current best-supported theory:
      this specific WiFi chip/driver (`wl`, proprietary Broadcom,
      confirmed via `readlink /sys/class/net/wlan0/device/driver`) has
      an inherent multi-second firmware-load/PHY-init time on every
      power-up, and GDM/Mutter's own greeter startup independently takes
      a similar amount of time for unrelated reasons -- the two are
      NOT causally linked (proven by the NetworkManager-wait-online
      test above), they just keep landing in the same few-second window
      by coincidence of similar duration. Not fixed. Actually chasing
      this further would mean investigating the `wl` driver's own
      firmware-load timing specifically, a much lower-level undertaking
      than anything else attempted tonight.
    - The core intermittent symptom itself (lid-open sometimes resumes
      cleanly, sometimes leaves the screen dark until a power-button
      press) is NOT root-caused. Verified via direct sysfs instrumentation
      that `/sys/class/backlight/intel_backlight/bl_power` does NOT
      reliably reflect the actual physical panel state on this hardware
      (caught it reporting "on" for 4+ continuous seconds while the user
      was directly looking at a black screen) -- so this exact sysfs
      node cannot be trusted as a ground-truth signal for future
      investigation; a different instrumentation approach (DRM connector
      dpms state, or direct human-timed observation) would be needed.

19. *** SUSPEND/WAKE: SOLVED *** s2idle + suspend-then-hibernate
    THIS SUPERSEDES items 14, 15 and 19. Final working configuration:
      /etc/systemd/sleep.conf:   MemorySleepMode=s2idle
                                 HibernateDelaySec=15min
      /etc/systemd/logind.conf:  HandleLidSwitch=suspend-then-hibernate

    Behaviour: close the lid -> s2idle (wake in ~2s with a key tap).
    If still closed after 15 min -> automatically performs a REAL
    hibernate and fully powers off (fan stops). Waking from that takes
    ~40s (Limine -> image restore) and returns the exact session, apps
    still open. Verified end to end:
      12:15:46  PM: suspend entry (s2idle)
      12:16:17  PM: hibernation: hibernation entry   <- auto, 31s later
      12:18:00  PM: hibernation: hibernation exit    <- same boot ID
    User confirmed: fan physically stopped during hibernation, ~2-3s to
    the Limine menu on wake, and all apps were still open afterwards.

    WHY THIS WORKS WHERE THE EARLIER ATTEMPT FAILED (item 14):
    suspend-then-hibernate needs to wake itself on a timer to perform the
    transition. Under deep S3 that is impossible on this hardware -- the
    RTC has no _PRW method in Apple's DSDT, so it is not a valid ACPI
    wake source (see item 14 for the full DSDT evidence). Under s2idle
    the machine is only FROZEN, not powered down, so an ordinary timer
    interrupt is enough -- no ACPI wake source needed. Switching the
    intermediate state from deep to s2idle is what unlocked it.

    MEASURED POWER (on battery, energy_now deltas):
      awake, idle          7.37 W
      s2idle ("asleep")    4.16 W   <- only ~43% better than awake!
      hibernated           ~0 W
      one hibernate cycle  ~0.45 Wh fixed (write image + resume + POST)
    Break-even: 0.45 Wh / 4.16 W = ~6.5 min. Any sleep longer than that
    is cheaper hibernated. Battery cost of the 15 min delay window:
    ~2.6% (s2idle) + ~1.1% (transition) = ~3.7% of a 40.6 Wh battery.
    A 1h delay would have cost ~11.3%, which is why the systemd default
    of 1h is a bad fit here -- that default assumes the intermediate
    state is a real ~0.5 W S3, which this machine cannot use.

    WHY NOT PLAIN deep S3 (the "obvious" answer): it is BROKEN and
    genuinely unsafe on this machine. Wake took 9-40 s when it worked at
    all, and it repeatedly hard-hung the laptop -- keyboard, trackpad,
    power button, AC plug and USB all did nothing, requiring a ~10 s
    forced power-off. BTRFS survived each time (`btrfs device stats`
    all zeros) but that is luck, not a plan. Do not switch
    MemorySleepMode back to deep.

    ALSO CHANGED WHILE GETTING HERE (all kept, all verified):
    - EC (PNP0C09) enabled as a wake source in /proc/acpi/wakeup.
    - SPIT (APP000D, the Apple SPI keyboard/trackpad controller) enabled
      as a wake source, persisted via /etc/systemd/system/
      enable-spit-wake.service (ACPI wake states reset every boot).
      This is what makes the 2 s key-tap wake work.
    - Kernel cmdline: nvme_core.default_ps_max_latency_us=0 nvme.noacpi=1
      (NVMe APST/ACPI power-state workarounds). Applied while deep S3 was
      still in play; did NOT fix deep S3, but harmless and kept.
    - /etc/systemd/system-sleep/disable-d3cold (drops d3cold_allowed to 0
      on every sleep). Same story -- didn't fix deep S3, kept anyway.
    - NetworkManager-wait-online.service disabled (was 4.174 s in
      systemd-analyze blame). Small boot win. DISPROVEN as a cause of the
      GDM/Plymouth delay -- plymouth-quit-wait stayed at 7.2 s with it
      gone.

    KNOWN REMAINING QUIRK (accepted, not a bug we can fix):
    Opening the lid does NOT wake it from s2idle -- a key tap is needed.
    The lid event IS received (PNP0C0D:00 wakeup counter increments and
    logind logs "Lid opened"), but under s2idle the kernel only treats an
    SCI as a wake if it came from a GPE armed specifically for wake, so
    the event is processed without ending the s2idle loop. The keyboard
    works because it goes via xHCI. Enabling EC/LID0/SPIT in
    /proc/acpi/wakeup did not change this. Workflow is: open lid, tap a
    key. Waking from the hibernated state uses the power button normally.

    ALSO WORTH KNOWING: the fan cannot be stopped on this hardware.
    Verified empirically -- stopped mbpfan, wrote 0 to both fan1_min and
    fan1_output, and the SMC kept it at ~1190-1220 RPM for a full 60 s
    while temps sat flat at 53-54 C. The writes are accepted (readback
    changes) but the SMC firmware clamps actual behaviour to its own
    ~1200 RPM floor. macOS idles these at ~1200 RPM too. mbpfan's
    min_fan1_speed=1200 matches that floor and is already as quiet as
    this machine gets. The fan DOES stop when genuinely hibernated,
    which is a useful way to confirm hibernation actually happened.

20. HARDWARE THERMAL MODS: physical repaste + heatsink-to-bottom-case pad
    User did both, independently, with a standardized before/after
    benchmark between each step (all-core stress-ng --cpu 4, 90s, at the
    stock 3300MHz cap, always cooled down to a fixed starting temp first
    so the three runs are genuinely comparable):
      /tmp/thermalbench.sh <label>   -- waits for cooldown to a target
      temp, runs the load, reports bogo-ops/s (real throughput -- the
      metric that matters), max temp, fan RPM, throttle event count, and
      throttle_total_time_ms (a far better metric than count alone, since
      a handful of long stalls and many short blips can report similar
      counts but very different actual impact).

    RESULTS:
                     bogo-ops/s   max temp   throttle time (of 90s)
      stock            2662.80      97C      10.1%
      + repaste        3303.67     100C      32.7%   <- see note below
      + pad mod         3582.82     98C       0.0%   (3ms total)
      Overall gain: +34.6% throughput, throttling essentially eliminated.

    NOTE on the repaste-alone throttle% going UP while throughput ALSO
    went up (not a contradiction): fresh paste lowers die-to-heatsink
    thermal resistance, so the chip both HEATS to the 100C ceiling faster
    under load AND cools/recovers faster once it backs off -- net effect
    is more frequent but much shorter throttle blips, with more real work
    done between them. bogo-ops/s (actual throughput) is the trustworthy
    number here, not the throttle percentage in isolation.

    The pad mod (bridging the heatsink to the aluminum bottom case with
    thermal pad) is what actually fixed the underlying problem: the
    heatsink alone was saturating and had nowhere further to put the
    heat, causing the repeated throttle cycling seen above. Giving it a
    second path into the whole bottom case removed that ceiling almost
    entirely -- same peak temp (~98C) but the machine can now sit there
    continuously instead of bouncing off it.

    Idle floor also dropped sharply as a side effect: ~68-73C before ->
    ~52-54C after both mods, at true idle on AC.

    Machine: MacBookAir6,1 (A1465, 11"), i7-4650U. Physical work (paste
    application, pad placement) done by the user; measurement/comparison
    done remotely via SSH. No specific thickness spec exists for this
    model in the community (mod is mostly documented for fanless M1/M2
    Airs) -- gap was measured directly via the squashed-clay technique
    rather than assumed.

21. RAPL POWER LIMITS (PL1/PL2); CORRECTION BELOW: enforcement is NOT
    functional on this platform. Kept as documentation-only/harmless.
    *** IMPORTANT CORRECTION (found immediately after writing the below):
    the throughput comparison across 10W/15W/20W/uncapped was NOT showing
    "no cost to staying within spec" -- it was showing that NONE of these
    settings were ever actually being enforced. Verified directly:
      - Raw MSR read (0x610, MSR_PKG_POWER_LIMIT) after setting PL1=10W:
        decodes correctly to PL1=10W enabled+clamped, PL2=25W enabled,
        LOCK BIT CLEAR (not locked, unlike the voltage mailbox/C-state
        MSRs found earlier tonight -- confirmed via MSR_RAPL_POWER_UNIT
        0x606 for the 0.125W/unit scaling). So the register itself is
        correctly configured, unlocked, and enabled.
      - Despite that, measured ACTUAL sustained package power (via
        intel-rapl energy_uj deltas) over a full 80-second continuous
        load with PL1=10W active: flat 21.6-23.0W the ENTIRE time, never
        approaching 10W at any point, even though 80s is more than 3x
        the ~24.6s PL1 averaging window (RAPL enforces a rolling average,
        not an instant cutoff, so a short sample can't rule this out --
        an 80s sample can).
    CONCLUSION: RAPL power-limit enforcement does not functionally work
    on this platform/microcode, regardless of what value is configured.
    The register faithfully stores and reflects whatever is written, but
    the CPU's power control unit does not act on it -- the chip just
    runs at its natural ~22-23W thermally-limited draw regardless.
    set-rapl-limits.service is harmless (replaces a nonsensical 100W/
    125W-with-2.44ms-window placeholder with honest, documented 15W/25W
    values) but has NO actual effect on real CPU behaviour on this
    hardware. Do not rely on RAPL for power/thermal control here -- the
    only things that actually changed real behaviour tonight were the
    physical thermal mods (item 20: repaste + heatsink-to-case pad).
    Left enabled anyway since it's zero-cost and self-documenting; not
    worth chasing further (would mean digging into PCU/microcode
    internals, well past what's reasonable to pursue here).

    ORIGINAL (now-corrected) writeup follows, for the record of what was
    actually tested and measured:
    Discovered while investigating the throttling seen in item 20's
    "before" numbers: this platform's firmware ships RAPL with
    essentially no real limit at all --
      PL1 (sustained):  100 W   (chip's actual TDP is 15 W)
      PL2 (short-term): 125 W,  with a 2.44 ms time window (should be
                                 several seconds -- this window is so
                                 short it's functionally meaningless)
    So the CPU was running purely thermally-limited with no designed
    power budget, relying entirely on hitting 100C as its only guardrail
    -- consistent with the throttle-thrash behaviour measured in item 20.

    Set via the standard powercap interface (safe, no MSR unlock needed
    -- this is a different MSR/mechanism than the undervolt mailbox that
    hit OC_LOCK earlier tonight):
      /sys/class/powercap/intel-rapl/intel-rapl:0/constraint_0_power_limit_uw
      /sys/class/powercap/intel-rapl/intel-rapl:0/constraint_1_power_limit_uw
    Persisted via /usr/local/bin/set-rapl-limits.sh +
    /etc/systemd/system/set-rapl-limits.service (enabled, multi-user.target
    -- powercap values reset to firmware defaults every boot, same as
    ACPI wakeup/MSR states elsewhere in this file).

    TESTED THREE CONFIGURATIONS, same standardized thermalbench.sh, same
    stock 3300MHz cap, same cooldown-to-55C-first methodology as item 20:
                           bogo-ops/s   max temp   throttle%
      "uncapped" (broken)   3582.82       98C        0.0%
      PL1=20W / PL2=28W     3575.03       99C        0.4%
      PL1=15W / PL2=25W     3636.80       99C        0.3%   <- CHOSEN
    All three within ~2% of each other -- noise, not a real difference.
    Also independently measured actual sustained package power draw
    during load (via intel-rapl energy_uj counter) BEFORE setting any
    limit: ~22.2 W steady-state at "uncapped" settings -- i.e. even with
    no power limit at all, the improved cooling never pushed the chip
    meaningfully above what a sane limit would allow anyway.

    CHOSE SPEC VALUES (PL1=15W/PL2=25W), NOT the more aggressive 20W/28W
    initially proposed: the pad mod + repaste improved cooling enough
    that the chip does not need to exceed its documented 15W TDP to hit
    full sustained performance -- there is no measurable throughput cost
    to staying within Intel's validated envelope, so the conservative
    choice (better for long-term VRM/battery/thermal-cycling wear) was
    free. PL1 window ~24.6s, PL2 window ~8s (both requested as 28s/8s;
    RAPL's time-window encoding only supports discrete steps, so they
    were quantized slightly by hardware -- both close enough to intended
    and this is normal, not a bug).

    NOTE: one comparison run (PL1=15W/PL2=25W, first attempt) got
    contaminated by multiple overlapping test invocations left running
    concurrently from earlier interrupted attempts, producing 3 different
    inconsistent result sets in the same log window. Confirmed nothing
    was still running (`ps aux | grep stress-ng`), then reran once,
    cleanly, in isolation -- that clean rerun (3636.80 bogo-ops/s) is the
    number used above. If retesting RAPL values in the future, always
    verify no stray stress-ng/thermalbench processes are running first.

    FOLLOW-UP that revealed the correction above: also tested PL1=10W
    (PL2 left at 25W) -- 3619.05 bogo-ops/s, 99C, 0.2% throttle, again
    statistically identical to every other setting tried. That prompted
    directly measuring real sustained power draw (intel-rapl energy_uj
    delta) rather than trusting the throughput numbers alone: ~22.6W
    over a quick sample, then confirmed with a full 80-second continuous
    sample at 8s intervals (21.6-23.0W throughout, never dropping toward
    10W). This is what led to decoding the raw MSR 0x610 and discovering
    RAPL enforcement itself doesn't function on this platform (see
    correction at the top of this item).

    way). Worth re-checking if throttling behavior seems to drift again.

    Linux - a macOS-side richness gap, not something left unfixed here.
